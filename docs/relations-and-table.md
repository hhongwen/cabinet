# 卡片关系与表格视图

> 2026-11-24 需求立案。这份文档只做一件事：把「卡片之间怎么连」和
> 「怎么像多维表格那样看」这两件事的技术判断写下来，**不写实现**。
>
> 起因是实际使用中反复出现的四件事：一条随手记记错了（欧加隆/诺华写串）、
> 两张卡其实是同一件事、一张卡里塞了四个诉求、分期的任务第二期找不到第一期。

---

## 一、先分清三种关系

这三种经常被混成一个词「关联」，但它们的**生命周期完全不同**，
放同一张表里必然打起来。

| 关系 | 方向 | 语义 | 举例 | 生命周期 |
|---|---|---|---|---|
| **派生**（合 / 拆） | 有向，不可逆 | 这张卡**从**哪来 | 两张卡合一张、一张拆成三张 | 建立后**永不改动** |
| **层级**（父子） | 有向，可重组 | 这条**属于**哪件事 | 「V24 报表修复」下面挂 12 条 | 随时可拖进拖出 |
| **依赖**（前置） | 有向，可成环检测 | 这条**做完才能做**那条 | 架构变更通知 ← 依赖 RIS 表对接 | 随进度变，且**可以有环的** |

**为什么不能合成一张表**：派生关系是「历史事实」（我明明是从这两条合过来的，
不能因为后来重组了就说你没从这来）；层级是「当前组织」（今天挂这儿，
明天可以挂别处）；依赖是「执行约束」（这俩互相依赖就是环，必须报错）。

三种混在一起，就会出现「我改了层级，结果合并历史也变了」这种事。

**但也不要建三张表**。三种都是「有向边 + 两端 + 一句说明」，
统一放在一张 `links` 表里，用 `kind` 区分，各自加约束即可。

```sql
CREATE TABLE links (
  id         TEXT PRIMARY KEY,
  kind       TEXT NOT NULL,        -- 'merge_parent' | 'split_of' | 'parent' | 'depends_on'
  from_id    TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  to_id      TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  note       TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  UNIQUE(kind, from_id, to_id)
);
CREATE INDEX idx_links_from ON links(kind, from_id);
CREATE INDEX idx_links_to   ON links(kind, to_id);
```

### 1.1 合并：`merge_parent`

需求里说的「标【合】，能看到原始的两张卡」。方向怎么定很关键：

**正确的方向是「新卡 → 旧卡」**。合并产生一张**新卡**（内容更完整的那份），
它指向被合并掉的每一张旧卡。旧卡不删除、不归档、不可再编辑，
只作为历史被引用。

```
合并前    A（随手记：筛选条挪位置）     B（随手记：减少纵向空间）
            ↓ 合并
合并后    C【合】筛选条挪到标题行右侧
            ├── merge_parent → A
            └── merge_parent → B
```

**为什么不是「把 B 的内容塞进 A，A 变主卡」**：那样 A 的身份既是「原来的 A」
又是「合并后的 A」，历史读起来是错的 —— 三个月后你看到 A 的 created_at
是第一次记下的时间，但它其实还包含第二次记下的内容。新建一张 C 最干净：
C 的出生时间就是这次合并的时间。

**合并的三个硬约束**（不写进代码就会出事）：

1. **旧卡进 `merged_into` 状态**，不是 `archived_at`。归档的语义是「做完了」，
   被合并的语义是「它变成了别人」。两者的视图入口、可编辑性、能否取回都不同。
2. **旧卡的对话和附件不搬走，只被引用**。搬走就等于删了 —— 而合并的前提
   恰恰是「不能因为合并丢失原卡」。
3. **合并可撤销**：撤销 = 删掉 C 的 `merge_parent` 边 + C 进 `merged_into`，
   让 A、B 回来。**这是唯一需要「反向」操作的关系。**

### 1.2 拆分：`split_of`

拆的方向和合并相反：**旧卡 → 新卡**。

```
拆分前    A（一条卡里 4 个诉求）
            ↓ 拆分
拆分后    A【拆】(变成容器，本身不再有 status)
            ├── split_of → B（P2 常规·工作 那个标签是什么）
            ├── split_of → C（提示文字不居中）
            ├── split_of → D（输入文字居上）
            └── split_of → E（按钮不齐平）
```

**这里有个坑**：拆完之后 **A 还要不要有状态**？

- 如果 A 保持 `todo`，它和 B~E 会同时出现在看板上，等于同一件事数了 5 遍
- 如果 A 进 `archived_at`，语义又错了（它没做完，它被拆了）

所以拆分需要一个**第四种状态**：`split`。它在看板上不占列，
在「拆分」视图里能看到，点开是 B~E 的清单。

**但更简单的做法是不引入新状态**：拆完直接把 A 标成 `done`，
备注写「已拆分为 4 条，见子项」。理由是拆分这个动作**确实结束了** ——
一件含糊的事被拆成了四件清楚的事，原卡的历史使命完成了。

> 我的判断：**先按「done + 备注」做**，等你真的觉得需要在「拆分视图」里
> 翻旧账时再引入 `split` 状态。多一个状态就多 7 处要改（`STATUSES`、
> `applyStatus`、`counts`、`COLS`、`STATUS_LABEL`、导航映射、拖拽目标）。

### 1.3 层级：`parent` / `child`

这就是飞书多维表格那个「层级」列 —— 表格里第 1 列那个可以折叠的树。

**它和「合并」最容易混，区别在这里**：

| | 合并 | 层级 |
|---|---|---|
| 谁是谁 | 两张卡**变成**一张 | 一条**属于**另一条 |
| 内容 | 新卡内容是旧卡的**并集** | 父子各自有独立内容 |
| 数量 | 2 → 1 | N 条挂在 1 条下面 |
| 能改吗 | 不能（历史事实） | 随时拖进拖出 |

截图里那个表就是纯层级：`【2025NCF流程】` → `【V24-报表调整】` → `RX` →
`主流约TVD结算流程` → `1. 五险的底稿/逻辑 - 文档更新交换`。
**五层**。而且每一层都是「一件事」，不是一个动作。

**层级要加三条约束**：

1. **不能成环**（A 的父是 B，B 的父是 A）。写的时候必须查一次祖先链。
2. **深度上限**（建议 5 层，和截图一致）。超过就该拆项目，不是加深层级。
3. **父卡的 status 是派生的**，不是手填的 —— 子项全 done 才算 done。
   否则会出现「父卡写着已完成，下面 3 个子项还在 doing」。

这条第 3 点是**和现有 `status` 最大的冲突**：现在的 `status` 是人手改的，
层级一进来它就得变成「手改 + 派生」两套并存。要么接受这个复杂度，
要么明确规定「有子项的卡，status 只读」，后者更简单。

### 1.4 依赖：`depends_on`

需求里说的「依赖的卡片执行完才能执行新的卡片」。

```
「实现组织架构变更定时检查通知」
    ├── depends_on → 「补齐 HeadCount 审查的 RIS 表对接」
    └── depends_on → 「架构变更事件埋点」
```

**依赖和层级不能混**：层级是「我属于谁」，依赖是「我要等谁」。
上面那个例子，两条前置都不属于通知那条卡，它们只是必须先做完。

**依赖的四个约束**：

1. **可以在不同项目之间**（层级通常同项目，依赖经常跨项目）
2. **必须能检测环**：A 等 B，B 等 A，两条都永远卡住。加边时就要查。
3. **前置没 done 时，被依赖的卡不能进 `doing`** —— 拖到「进行中」要被拦，
   提示「还等 2 条前置」。这跟 `dev_ready` 的拦截是同一个机制。
4. **前置卡被删 / 被合并时怎么办**：级联删掉这条边，并在被依赖的卡上
   留一条提示「原来的前置 X 没了，重新确认」。

**依赖不要做成「自动执行」**。它只是**约束**，不是调度器 ——
CI/CD 那种自动触发是阶段 2 的事，现在做就是给自己挖坑。

## 二、标签怎么显示

需求里说的【合】【拆】。三个选项：

| 方案 | 怎么做 | 好处 | 坏处 |
|---|---|---|---|
| A. 标题前缀 | `【合】xxx` | 改动最小，一眼看到 | 污染标题，搜索/排序都会带上 |
| B. 独立徽章 | 卡片上一个 `<span class="tag merge">合</span>` | 语义干净，可以点击跳转 | 要动卡片布局 |
| C. 图标 | 一个小的合并/拆分 SVG | 最省地方 | 13px 下认不出来 |

**建议 B**：现在卡片上已经有 `P2 常规 / 开发 / Cabinet / 图文` 一排徽章了，
加两个新颜色成本很低。而且**徽章可以点击** —— 点【合】直接展开原始的
那两张卡，这正是需求里要的「能通过这个卡片看到原始的两个卡片」。

**但要注意**：徽章多了会挤爆一行。现在 `cardHTML` 里 `.meta` 已经
`flex-wrap` 了吗？如果没有，加之前得先确认。13 个徽章的极端情况要有兜底。

## 三、表格视图

截图那个飞书多维表格，核心是四件东西。逐条看现在缺什么：

| 能力 | 现在 | 缺口 |
|---|---|---|
| **层级折叠**（第 1 列那棵树） | 无 | 需要 `parent` 关系 + 递归渲染 |
| **自定义字段列** | 固定：优先级/项目/类别/状态 | 缺「预估工时」「负责人」这些业务字段 |
| **按字段分组**（截图的「Group By」） | 只有侧栏硬编码的筛选 | 需要通用分组 |
| **行内编辑** | 抽屉里才能改 | 表格要能直接点格改 |

### 3.1 表格视图需要哪些列

从截图抄下来的列，对照现有字段：

| 截图列 | 现在有没有 | 备注 |
|---|---|---|
| 编号 | `id`（26 字符） | 需要一个**短编号**（`T-001` 这种），否则表格里放不下 |
| 名称 | `title` ✅ | |
| 状态 | `status` ✅ | 但截图有「测试中」这一档，现在只有 todo/doing/done |
| 开始时间 | `doing_at` | **语义不同**：这是「实际开始」，截图那个是「计划开始」 |
| 结束时间 | `done_at` | 同上，是实际完成 |
| 研发人员 | `claimed_by` | 只有一个，截图可以多人 |
| 需求负责人 | ❌ | 没有这个字段 |
| 预估工时 | ❌ | 没有 |
| 实际工时 | ❌ | 没有 |

**所以表格视图不需要新发明东西，只需要补四个字段**：

```
tasks 加：
  seq_no         INTEGER   短编号（T-001），迁移时按 created_at 顺序填
  plan_start_at  TEXT      计划开始
  plan_end_at    TEXT      计划结束
  owner          TEXT      需求负责人
  estimate_hours REAL      预估工时
  actual_hours   REAL      实际工时
```

`doing_at` / `done_at` 保留不动 —— 它们是**事实**，计划时间是**意图**，
两回事，别合并。

> **但先别加这 6 个字段。** 表格视图最缺的不是列，是**层级**。
> 没有层级，表格就是一长条平铺的卡，和现在的看板没区别。
> 先做关系（第一节），表格只是换一种渲染方式。

### 3.2 表格和看板的关系

**不是两个页面，是同一份数据的两种渲染。** 切换按钮在顶部，
状态记在 `localStorage`（`ti.viewMode` = `board` | `table`）。

理由：如果做成两个页面，筛选状态、滚动位置、当前项目全都要各存一份，
两边永远对不上。渲染函数分开，数据源必须是同一个 `store.tasks`。

**表格视图里哪些东西不能丢**：

- 点一行 → 打开同一个抽屉（不能另做一个编辑面板）
- 拖拽换列 → 表格里是拖「状态」那一格，语义和看板一致
- 折叠箭头 → 只影响渲染，不改数据

### 3.3 分组（Group By）

截图里是「1 Group By」，按状态分组。现在侧栏的筛选是硬编码的
（全部任务/待澄清/未开始/进行中/已完成/归档）。

**通用分组 = 把现在硬编码的那一套，换成「任意字段可分组」**。
但这一步会直接和 `inView()` 的流水线逻辑冲突 ——
流水线是有序关卡，分组是无序分桶。

**建议：分组只对表格视图开放，看板保持流水线不变。**
看板的列就是流水线本身，不允许重排；表格的分组是一层额外的视觉组织。
这两件事别互相污染。

## 四、落地的顺序（重要）

这四件事一起做会失控。建议分四步，**每步都能独立用起来**：

| 步 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **1** | `links` 表 + 合并/拆分 + 【合】【拆】徽章 | 这是最痛的一条（已经丢过一次内容了）。不依赖表格、不依赖层级 |
| **2** | 依赖（`depends_on`）+ 拦截 | 纯后端约束 + 一处拖拽拦截，不碰 UI 布局 |
| **3** | 层级（`parent`）+ 看板里折叠 | 要和 status 派生打架，得单独排 |
| **4** | 表格视图 + 6 个新字段 | 前三步的数据结构定了才谈得上「换一种渲染」 |

**第 1 步就能用起来**：现在那两条 worker 断连的卡，合并之后
【合】徽章点开能看到原始的欧加隆那条（写错的那条）—— 这就是需求里
要的效果，不需要等表格。

## 五、必须提前定的事（不定就会返工）

1. **被合并的卡，用户还能编辑吗？**
   建议：**只读**。它已经是历史了，改它等于改历史。要看内容可以点开，
   但不能改标题/状态/项目。

2. **合并时用户手动选主卡吗？**
   建议：**模型给建议 + 用户确认**。模型看两张卡的内容，说「B 完整度更高，
   建议以 B 为基准」，用户点确认或改选。和 `dev_ready` 的判定是同一套哲学。

3. **层级和项目的关系？**
   现在项目是一层平的组织（`projects` 表）。如果加层级，
   **「项目」要不要变成「层级的一个根节点」**？
   建议：**不要**。项目是「这条属于哪个客户/仓库」，层级是「这条属于哪个需求」。
   两者是不同维度，硬合并会让「跨项目需求」无处安放。

4. **依赖能不能跨项目？**
   建议：**能**。否则「诺华改了接口 → 爱琅要跟着改」这种就没法表达。

5. **表格视图要不要支持多人？**
   截图里「研发人员」可以挂多个人。现在 `claimed_by` 是单值。
   建议：**先单值**，真到要多人那天再说 —— 一个人用不着。

## 六、和现在这套的关系

- **不改流水线**：待澄清 → 未分配 → 看板 → 归档 那条链不动
- **不改 `STATUSES`**：除非真的做「拆分进 split 状态」（我建议先不做）
- **不改 `dev_ready`**：它是「够不够开工」，和依赖是两件事
  （一条卡可以足够清楚，但前置没做完）
- **`links` 是新表**。设计时以为「不动 `tasks` 表」，实现时发现
  **必须动**：`merged_into` 得落在 `tasks` 上，否则每次判断「这张卡是否只读」
  都要 join 一次 `links`，而那个判断发生在 `patch()` 的最热路径上。
  > 上一版这里写「第一步完全不需要 schema 迁移，只加一张表」——
  > 实现时否掉了。**加一张表 + 两个列**，仍是 v5 一次迁移。

## 七、第 1 步落地记录（2026-11-24）

### 实际做了什么

| 层 | 内容 |
|---|---|
| schema | **v5**：新增 `links` 表；`tasks` 加 `merged_into`、`split_state`（后者本轮只占位） |
| core | `linkTasks` / `unlinkTasks` / `deleteLink` / `listLinks` / `mergeTasks` / `splitTask` / `revertMerge` |
| 接口 | `GET /api/tasks/:id/links`、`POST /api/tasks/merge`、`POST /api/tasks/:id/split`、`POST /api/tasks/:id/unmerge`、`POST /api/links`、`DELETE /api/links/:id` |
| 界面 | 卡片【合】【拆】徽章（可点）+ 关系浮层；抽屉「关系」区 + 「合并到别的卡」/「拆成几条」两个入口 + 头部「撤销合并」 |
| 测试 | `test-sqlite` 176 → **220**（合并、拆分、只读、撤销、级联删除、v4→v5 迁移） |

### 和设计稿不一致的地方（都是实现时发现必须改的）

1. **`buildWhere` 默认排除 `merged_into` 非空的卡**，`include_merged=1` 才看得到。
   设计稿里只说「旧卡不删不归档」，没说它们还占不占看板。实测如果照原样，
   合并完旧卡还挂在列里，等于没合并。所以加了这层默认过滤，**并且**
   `revision(scope)` 里带上 `include_merged` —— 两种请求返回体不一样，
   共用指纹会让前端拿到错的那份。

2. **`state()` 的 counts 也排除被合并的卡**。否则侧栏写 3、列里只有 1 条。

3. **关系区空态也要渲染**。第一版是「没有关系就整块不显示」，
   结果新卡永远看不到「合并到别的卡」这个入口 —— 第一次合并没有下手的地方。

4. **合并/拆分的输入用浮层，不用 `prompt`/`confirm`**。
   合并要勾选多张卡、拆分要写多行，原生对话框做不到。
   材质复用 `.picker`（z-index 72，要盖过抽屉）。

5. **撤销合并把新卡归档，不删除**。设计稿只说「撤销 = 删边 + 旧卡回来」，
   没说新卡怎么办。删掉会连人手写进合并卡的标题正文一起删 —— 那是真丢东西。
   归档后它留在归档视图里可查，`merged_into` 的旧卡全部解锁。

6. **删掉「合并出来的那张卡」时，旧卡的 `merged_into` 要清空**。
   否则它们永久只读、又没有任何卡能撤销回来 —— 等于锁死。
   这是 `remove()` 里一条额外的 `UPDATE`。

### 还没做的（第 2~4 步）

- 依赖（`depends_on`）+ 前置未完成时拦拖拽
- 层级（`parent` / `child`）+ 看板折叠渲染 + 父卡状态派生
