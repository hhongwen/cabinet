# Cabinet 目标定义

> 这份文件只定「要什么」和「不要什么」。
> 实现方案另开 DESIGN.md，不在本文展开。

---

## 一、一句话目标

**Cabinet 是任务编排器，不是 Agent，也不管模型。**

它接收任务、把任务整理成一张有依赖关系的图、自动调度执行、
在需要人拍板时停下来问，并把整个过程留在可查的记录里。

---

## 二、三层分工（这是整个方案的地基）

```
Cabinet   任务编排层   任务图 / 依赖 / 优先级 / 调度 / 群消息 / 审批
Magpie    模型供给层   12 个 agent、5 个 provider、routing group、quota
Agent     执行层       codex / opencode / dsh / pi，自带 session
```

**Cabinet 不许出现的东西**：provider 名单、API key、模型列表、计费逻辑。

**Cabinet 只认两个东西**：`agent` 名字（codex/opencode/dsh/pi），
和 `model` 标识（形如 `magpie/auto/deepseek-v4.1-flash`，原样透传给 agent CLI）。

> 判断标准：任何一条「Cabinet 要知道有哪些模型可用」的需求，
> 都应该是「去问 Magpie」，而不是「在 Cabinet 里配一份」。

### 为什么不给 Magpie 写插件

Magpie 的插件是「接模型供应商」用的（OpenCode provider plugin / gateway hook），
不是给外部系统读配置用的。而它已经有两个现成出口：

- CLI：`magpie ls`（所有 agent + 当前模型）、`magpie models <agent>`（该 agent 可用模型）
- 网关：`http://127.0.0.1:3425/v1`，OpenAI 兼容，`/v1/models` 返回全部模型 + routing group

写插件是侵入式的，Magpie 一升级就可能挂。读现成出口是零耦合。

**附带收益**：Cabinet 自己需要 LLM 做任务拆解/分类时，直接调这个网关。
不碰任何 key，用你配好的 routing group。

## 三、要什么

### 3.1 任务是一等对象（不再是事件）

| 概念 | 说明 |
|---|---|
| **Project** | 一个 cwd + 它的 AGENTS.md + 一组群 + 一组任务。项目边界就是目录边界。 |
| **Task** | 可嵌套（`parent_id`）。有标题、优先级、依赖、指派的 agent/model。 |
| **TaskRun** | 一次执行尝试。原来的 job 降级成这个。一个 Task 可以有多次 run（重试、换 agent 重跑）。 |
| **Session** | agent 那边的真实会话。`(agent, agent_session_id, cwd)`。TaskRun 关联它。 |

任务可以**拆**（一个拆成 N 个子任务）和**合**（N 个并成一个）。

**拆解由 Cabinet 自动完成（调 LLM），不需要人事先同意。**
人只在两种情况下介入：
- 拆解结果有模糊项（判据见 DESIGN.md 3.1）
- 有子任务带外部副作用（发消息、提 PR、发邮件）

其余情况自动进图、自动执行。人随时可以退回重拆。

判据不用「模型说自己有没有信心」——那个无法验证。
用结构化作答的完备性：每个子任务必须填全 cwd / done_when / agent，
填不全就说明需求本身就模糊。

### 3.2 依赖与自动调度

- `deps: [task_id]` 声明前置。全部 done 之前，任务不可执行。
- `priority` 整数，越大越先跑。同等优先级按创建时间。
- 调度器每 tick：找 ready 的任务 → 排序 → 受并发限制 → 抢占式 claim → 起 TaskRun。
- 并发限制两层：项目级 + 任务级（沿用现在 `concurrency.key/max` 的思路）。

### 3.3 群是统一的沟通抽象

这不是六个功能，是同一个东西的六种用法。**群 = 消息容器 + 订阅者列表。**

| 群的作用域 | 谁在里面 |
|---|---|
| **项目群** | 该项目下所有 session |
| **任务群** | 处理同一任务链的所有 session |
| **模块群** | 子任务之间的协调频道 |

消息有 `sender`：`human` / `session` / `system`。

面板上：看到消息流 → 点消息跳到所属 session → 点 session 看它的完整上下文。
这是一条链路，不是三个页面。

### 3.4 session 之间的沟通：轮次式

单个 agent 进程是无头一次性的，跑完就没了。**采用轮次式，不做实时。**

```
一轮 = 起一次 agent 进程 → 用 -s <agent_session_id> 续上上下文
     → prompt 里注入「群里这段时间的新消息」
     → 跑完，解析结论
     → 若结论里声明要找某个 session，就投消息到群并唤起对方
```

理由是可靠性：实时模式下 agent 得主动去「查收」消息，
它记不记得查是整个系统能否正常运转的唯一关键，不值得赌。
轮次式每轮都强制喂消息，不依赖模型的自觉。

### 3.5 人机边界

- **审批**：任务执行前需要批的，停下来等（沿用现有 `approval: before`）。
- **决策**：执行中需要拍的，agent 按协议输出，Cabinet 置为待办。
- **待办列表**：一个统一的入口，所有等你确认的事都在这里。面板和飞书都能看。

### 3.6 可视化

- 任务看板：状态列 + 优先级 + 依赖关系可见
- 群消息流：实时、可点、可追溯到 session
- session 抽屉：完整 prompt / transcript / 结论 / 耗时 / 成本
- 待办列表：一眼看完所有等你的事

## 四、不要什么（明确砍掉）

### 4.1 不做抢占式优先级

高优先级任务**不会**把正在跑的任务踢掉。
只做排序，不做抢占。

代价：一个跑了 8 分钟的 codex 被踢，会话上下文全废，还得重来。
收益：极小。人真正着急时会自己去 `reject`。

### 4.2 不让 agent 直接改任务图

**这条约束的对象是「执行中的 session」，不是拆解器。**

拆解器（建图的那个）可以自动拆，因为它是独立一步、产物可审、可整体回退。
但一个已经在跑的 session **不许**自己给自己加任务、改依赖、调优先级——
那等于运行中的代码改自己的调度表，出错时无法定位。

session 想改图，只能提议：输出 `@提议 ...`，Cabinet 落成待办，等人确认。

### 4.3 不做实时群聊

见 3.4。轮次式。

### 4.4 飞书走长连接，不改单机定位

> **修正**：早先的判断（飞书双向必须公网地址）是错的。
> 飞书开放平台的「事件订阅」支持**长连接**方式，
> 由本机主动向飞书建 WebSocket，事件从这条连接推回来。
> 不需要公网 IP，不需要 cloudflared 或 Tailscale Funnel。

所以：

- 飞书**发消息进来**（任务入口）和**卡片按钮回调**（审批），
  都走同一条长连接，一期就可以做。
- 单机定位不变：默认只绑 127.0.0.1，没有任何入站端口。
- 仍然不做的事：把面板暴露到公网。面板始终是本机页面。

Node 24 已内置全局 `WebSocket`，这件事零依赖可做。

唯一的取舍：长连接需要进程常驻并维持心跳，
断了要重连。这属于工程细节，不是定位问题。

## 五、要补什么（你没提但必须有）

### 5.1 失败重试策略

自动执行系统的生命线。没有它，「无人值守」就是个笑话。

- 可配置 `retry: { max, backoff }`
- 重试是「新建一个 TaskRun」，不是复用旧的
- 达到上限才置 `failed` 并进待办
- 重试原因（超时 / 非零退出 / 空结论）要记下来

### 5.2 任务完整时间线

一个任务从进来到结束，谁在什么时候做了什么决定。
这是「文件柜」这个名字的承诺，也是出问题时唯一的排查依据。

### 5.3 并发上限要有全局刹车

Magpie 那边有 quota（codex 7 天已用 88%）。
Cabinet 一次性拉起 10 个 codex，会把额度打爆。

需要在调度器里留一个「当前额度紧张就降并发」的钩子。
数据来源：`magpie quota --json`。一期可以先只打日志，不做自动降级。

## 六、分期

| 期 | 内容 | 验收标准 |
|---|---|---|
| **一** | Task 一等对象 + 依赖 + 调度 + 一个任务群 + 轮次式沟通 | 一个任务拆成两个子任务，两个 session 在同一群里交接，面板能看全程 |
| **二** | 优先级 + 待办中心 + 飞书长连接（收发）+ 失败重试 | 飞书发一句话能建任务；待办在飞书点按钮能批；失败自动重试一次 |
| **三** | 任务图可视化 + 拆合操作 + 额度感知降并发 | 图上能看到依赖，能拖拽拆合 |
| **四** | 任务图编辑 + 移动端体验打磨 | 手机上也能看清全局 |

一期跑不通，后面三期全是空谈。

---

## 七、判据

每当出现分歧，用这三条裁决：

1. **这件事是 Magpie 的活吗？** 是 → 不做，去问 Magpie。
2. **这件事会不会让「根」变得不可验证？** 会 → 不做，或降级成「提议 + 人确认」。
3. **这件事失败时，你能不能让责任追溯到某一条记录？** 不能 → 先补记录。
